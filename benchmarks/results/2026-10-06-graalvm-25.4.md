# Oracle GraalVM 25.4 (Innovation) vs Temurin 25.0.4.1 — 2026-10-06

Code under test: branch head `941a499`, the same installed jars and the same benchmark classes for every variant. Only the JVM binary and one JIT flag differ.

| Variant | JVM | Notes |
| --- | --- | --- |
| `temurin-c2` | Temurin 25.0.4.1+1 | HotSpot C2, the project's current JDK |
| `graal-jit` | Oracle GraalVM 25.4.4.1.1+1.1 (build `25.0.4.1.1+1-LTS-jvmci-25.4-b23`) | JDK 25.0.4.1 base, Graal compiler as the JIT (`UseJVMCICompiler=true`, the default) |
| `graal-c2` | same GraalVM | `-XX:-UseJVMCICompiler`: same distribution with C2, to tell compiler effects from distribution effects |

Decision rule, set before running: adopt a different JVM only if it is no worse on every workload and better on at least one beyond run-to-run range. Native-image was not tried: the proxy loads plugins through URL class loaders and runtime service discovery, which native-image does not support.

## Environment and method

Linux 6.18 container, 4 vCPU Intel Xeon, loopback, epoll transport, Netty 4.2.18, `-Xms512m -Xmx512m`, `-Dio.netty.leakDetection.level=disabled` (the distribution default). Each JVM runs `ProxySessionBenchmark --repeats 3` (three direct/proxy phases); five JVM runs per workload and variant, variant start order rotated each run. The first proxy phase of each JVM includes JIT warm-up; phases 2 and 3 are reported as "steady". Absolute proxy numbers are used because the in-process direct baseline shares the JVM and drifts. All 270 phases verified every echo, zero errors.

Workloads: `burst32` = 4 connections, 6000 round trips of 32 × 33-byte frames (window 4); `w1` and `w16` = 4 connections, 8000 round trips of 1 KiB (window 1 and 16).

## Interpretation

- **Graal JIT does not help and is worse on the small-frame burst workload.** Steady burst32: 24% lower throughput and 45% higher proxy I/O CPU per frame than Temurin, p95 0.890 vs 0.584 ms. The ranges overlap, but the medians separate in every metric, and the first (warm-up) phase is worse too (CPU 2421 vs 1571 ns/frame). On w1 and w16 there is no difference beyond range overlap; w16's median CPU per frame is higher with Graal JIT (6260 vs 5574).
- **The distribution itself is neutral.** `graal-c2` matches `temurin-c2` on every workload (burst32 steady 714 vs 752 ns/frame, 1.235M vs 1.226M frames/s), so the burst32 gap comes from the Graal compiler, not from GraalVM's JDK build.
- The decision rule is not met for `graal-jit`; staying on the standard C2 JIT is the evidence-backed choice. This does not exclude that the Graal JIT could win with much longer run times (each phase here lasts a few seconds) or on a different workload.

## Limits

One 4-vCPU loopback host with the benchmark client, fake backend and proxy sharing the CPUs; no Forge traffic, no online-mode encryption, and no memory (RSS) or total process CPU (including JIT compiler threads) measurement. Phases last only a few seconds, so "steady" means steady after the first phase, not after a production-length warm-up.
