## 实际服务验收

同一 JVM 内的两个独立 PluginHost、插件副本、类加载器和数据目录连接真正的 MariaDB/Redis。两个实例先加载相同 UUID，随后由 A 修改权限并等待 B 的已加载缓存更新，没有调用手工同步命令。SQL 模式使用 `messaging-service: auto`，日志确认选择原生 SQL messenger；Redis 模式使用 Redis messenger，权限仍写入 MariaDB。

| 场景 | 结果 |
| --- | --- |
| 跨实例授权、显式拒绝、撤销、组继承与个人覆盖 | 两种 messenger 均 PASS |
| 不同 server 上下文、临时权限到期 | 两种模式均 PASS |
| 关闭插件后以新类加载器读取持久化数据 | 两种模式均 PASS |
| MariaDB 停机：已有缓存仍可查，新 UUID 准备失败且结果为 UNAVAILABLE | PASS |
| MariaDB 恢复：新连接加载成功，新的权限写入可读 | PASS，首次恢复尝试成功 |
| Redis 停机：A 写入 MariaDB，B 缓存没有即时收到修改 | PASS |
| Redis 两个订阅恢复后：新变更同步到 B，重启 B 后可读取停机期间和恢复后的两项权限 | PASS |

最终数据库查询确认 `mariadb_lp_user_permissions` 有 6 行、`redis_lp_user_permissions` 有 5 行，恢复后的权限及 Redis 停机期间写入的权限均在 MariaDB 中。两轮验收均返回 `PERMISSION_NETWORK_ACCEPTANCE_PASS`，退出码 0；插件关闭后等待 500ms，没有未捕获后台异常。预期停机期间的连接失败日志不属于未捕获异常。

## 证据边界

本轮验证实际插件包与真实数据库服务，不包含新的游戏客户端、Uranium/Bukkit 联测、Web Editor 往返、远程 TLS 部署或生产数据迁移。既有 MySQL/H2/客户端记录保留为历史证据。Redis pub/sub 不补发断线窗口通知，不能据此宣称故障期间所有实例保持一致。
